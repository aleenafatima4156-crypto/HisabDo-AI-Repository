# Day 12 – AI Integration Architecture

## 1. Feature

Smart Expense Categorization

The purpose of this service is to automatically categorize
user expenses using a machine learning model.

---

## 2. Overall Architecture

User
  ↓
Website / Web Application / Mobile Application
  ↓
HisabDo Backend
  ↓
Flask REST API
  ↓
Input Validation
  ↓
AI Service
  ↓
TF-IDF Vectorizer
  ↓
Logistic Regression Model
  ↓
Prediction + Confidence
  ↓
Response Validation
  ↓
JSON Response
  ↓
HisabDo Application
  ↓
User

---

## 3. Step-by-Step Data Flow

### Step 1 – User Input

The user enters an expense such as:

"I bought groceries for dinner"

The application may also provide:

- User ID
- Amount
- Currency
- Date

---

### Step 2 – Application Request

The Website, Web Application, or Mobile Application
creates a JSON request.

Example:

{
    "user_id": "U001",
    "expense": "I bought groceries for dinner",
    "amount": 2500,
    "currency": "PKR",
    "date": "2026-08-12"
}

---

### Step 3 – Backend/API

The HisabDo backend sends the request to:

POST /categorize

The API receives the structured request.

---

### Step 4 – Input Validation

The API validates:

- JSON format
- Expense field
- Expense data type
- Empty description
- Maximum description length

Invalid requests are rejected with an appropriate error response.

---

### Step 5 – AI Service

The validated expense description is sent to
the Smart Expense Categorization service.

---

### Step 6 – TF-IDF Processing

The TF-IDF vectorizer converts the expense description
into numerical text features.

---

### Step 7 – Machine Learning Model

The Logistic Regression model receives the TF-IDF features
and predicts the most likely expense category.

The model also provides prediction probabilities.

---

### Step 8 – Confidence Handling

The highest prediction probability is used as the confidence score.

Current threshold:

0.40

If confidence is below the threshold:

Category = Uncategorized

This helps prevent unreliable automatic categorization.

---

### Step 9 – Response Validation

Before returning the result, the API checks that the required
response fields are available.

Required fields:

- status
- description
- category
- confidence

---

### Step 10 – JSON Response

Example:

{
    "status": "success",
    "user_id": "U001",
    "description": "I bought groceries for dinner",
    "amount": 2500,
    "currency": "PKR",
    "date": "2026-08-12",
    "category": "Food & Groceries",
    "confidence": 0.XX,
    "processing_time_seconds": 0.XXXX
}

The actual confidence and processing time are generated by the API.

---

### Step 11 – Application

The application receives the JSON response.

The predicted category can then be displayed to the user
and saved with the expense transaction.

# 7. Error Handling

The service handles:

### Missing Expense

Response:

{
    "status": "error",
    "message": "Expense description is required"
}

### Empty Expense

Response:

{
    "status": "error",
    "message": "Expense description cannot be empty"
}

### Invalid Data Type

Response:

{
    "status": "error",
    "message": "Expense must be a string"
}

### Long Description

The API rejects descriptions exceeding the configured
maximum length.

### Low Confidence

If model confidence is below 0.40:

{
    "category": "Uncategorized"
}

# 8. Security

Production deployment should include:

- HTTPS
- Authentication
- Authorization
- Input validation
- Rate limiting
- Secure logging
- Access control
- Protection of financial information

Financial data should not be unnecessarily exposed in logs
or sent to third-party services.

---

# 9. Data Privacy

Expense descriptions and transaction information may contain
sensitive financial information.

Therefore:

- Use encrypted communication.
- Limit access to financial data.
- Avoid unnecessary data collection.
- Avoid exposing financial information in error messages.
- Use secure database storage.
- Apply appropriate retention policies.

---

# 10. API Cost

The current POC uses a locally hosted ML model:

TF-IDF + Logistic Regression

Therefore, it does not require an external AI API for
each prediction.

This reduces per-request external API costs.

If an external AI API is used in the future, pricing,
request volume, rate limits, and data privacy must be considered.

---

# 11. Response Latency

The API records:

processing_time_seconds

This allows the development team to monitor response latency.

The current model is lightweight and is designed for
fast text classification.

---

# 12. Rate Limiting

A production API should implement rate limiting.

Possible controls:

- Requests per user
- Requests per IP address
- Requests per minute

When a limit is exceeded, the API can return:

HTTP 429 – Too Many Requests

---

# 13. AI Error Handling

The current system uses a traditional machine learning
classification model rather than a generative AI model.

Therefore, LLM-style hallucination is not the primary issue.

However, the model can still produce incorrect predictions.

To reduce this risk:

- Return confidence score.
- Use a confidence threshold.
- Return "Uncategorized" for low-confidence results.
- Allow user correction.
- Use corrected data for future model improvement.

# 15. Summary

The Day 12 architecture provides a reusable AI service
that can be consumed by the HisabDo Website, Web Application,
and Mobile Application.

The service accepts structured expense data, validates the
request, processes the description using TF-IDF, predicts a
category using Logistic Regression, calculates confidence,
handles uncertain predictions, validates the response, and
returns structured JSON to the application.
